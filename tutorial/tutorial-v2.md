# Locus 进阶指南

适用于 Locus 0.19.x。本篇假设你已经装好、配好渠道、跑通过至少一个 Agent 任务。如果还没有，先看 [上手指南](./tutorial.md)。

这里讲的不是功能清单，而是使用方式：怎么把上下文组织好，让同一个模型的输出质量明显不同。

---

## 一、上下文的三个层级

Locus 把上下文分成三层，每一层的生命周期不一样。搞清这一点，后面所有设计都是它的推论。

| 层级 | 载体 | 生命周期 | 作用 |
| --- | --- | --- | --- |
| 项目层 | 项目目录、`AGENTS.md`、项目级记忆、Skills | 长期 | 约束这个项目下所有会话的行为 |
| 会话层 | 会话、会话文件夹、对话历史 | 一次任务 | 完成一件具体的事 |
| 轮次层 | 单条消息、单次工具调用 | 一轮 | 一次交互 |

**常见的失败模式是层级混用**：把一次性资料塞进项目目录，让所有会话都被它污染；或者反过来，把项目的长期约定每次手动贴进对话，每次都要重复。

判断归属只问一个问题：**这份信息在下一个会话里还需要吗？** 需要就放项目层，不需要就留在会话层。

## 二、文件设计

### 什么是一个好的会话

一个好会话有三个特征：

- **目标单一**。一句话能说清这次要解决什么。
- **上下文自足**。只把这个会话需要的文件放进来，不多不少。
- **可结束**。做完就该结束，而不是永远挂着继续聊。

反过来，一个会话里塞进三个不相关的任务，是最常见的低效来源。模型的注意力被分散，前半段的内容在后面变成噪声。

### 文件怎么划分

**项目文件**：整个项目长期会用到的资料。代码、文档、参考资料、素材。多个会话共享。

**会话文件**：只服务这一次对话的输入。一次性的截图、临时导出的数据、某个特定版本的文档。

把一次性文件放项目目录的代价是：它会一直出现在后续会话可检索的范围内，而 Agent 并不知道它已经过期。

### 关于附加文件

一次拖十几个文件进来，通常不如只拖两个加上一句话说明。文件多了模型要自己判断哪个重要，而它往往判断错。

更有效的做法：**先说明要用哪个文件做什么，再拖文件**。语境在前，素材在后。

### 让文件本身携带语义

同一份内容，组织方式不同，Agent 的取用效率差很多。

- 文件名要说明内容，不要用 `文档1.md`、`新建文本文档.txt`
- 长文档加标题层级，让检索能定位到小节
- 分散的小文件如果总是一起用，合并成一个带索引的文件更好
- 数据类文件保留表头，别为了好看删掉列名

这些是给人看的规范，但对 Agent 同样成立——它读的也是这些文件。

## 三、记忆体系

Locus 的记忆不是"自动记住一切"，而是分层的、需要你参与维护的结构。

### `AGENTS.md`：项目宪法

放在项目根目录，每个会话自动注入。它应该回答：

- 这个项目是做什么的
- 目录结构和关键文件在哪
- 常用命令是什么
- 有哪些必须遵守的约定（命名、提交规范、不许碰的目录）

不该写进去的：一次性的任务说明、临时的调试结论、随时会变的待办。

写得过长会挤占上下文。经验值是控制在几十行，只留长期有效、违反就会出错的内容。

### `MEMORY.md`：记忆索引

记忆目录下的索引文件，指向更具体主题的记忆文件。它的作用是让 Agent 在需要时能找到对应主题，而不是把全部记忆一次性加载。

### 主题记忆

按主题分文件：你的偏好、项目的背景、某个系统的来龙去脉、决策的理由。

一条好的记忆记录的是**会影响未来判断的东西**，而不是事件日志。"用户偏好用 bun 而不是 npm"值得记；"今天修了一个 bug"不值得。

### 让 Agent 帮你建立记忆

如果你已经用了一段时间但还是空的，可以新开一个会话：

> 读一下最近一个月的会话记录，把其中稳定、可复用的信息整理成项目下 `AGENTS.md` 与记忆，按主题分文件，`MEMORY.md` 做索引。不确定是否稳定的先问我。

这里的关键是"不确定的先问我"。让 Agent 自己判断什么该记，很容易把一次性的判断固化成永久规则。

## 四、Skills

### 对 Skills 的正确认知

Skills 不是插件，是一段写给 Agent 看的操作手册：**什么时候用、按什么顺序做、有哪些坑**。

最好的 Skill 不来自互联网，来自你自己的真实流程。因为只有你知道在你的场景里哪一步容易出错。

### 怎么造一个 Skill

推荐的工作方式不是先写文档，而是**先做一遍**：

1. 开一个会话，手动带着 Agent 把这件事完整做一次，中途纠正它的错误
2. 做完之后说：「把刚才这套流程整理成一个 Skill，包括触发条件、步骤、每一步的注意事项和我纠正你的地方」
3. 检查它写出来的内容，把"看起来对但实际不对"的部分改掉
4. 下次真实使用时调用它，发现偏差就回来改

第 2 步里"我纠正你的地方"最重要——那些正是 Skill 存在的理由。

### 描述决定触发率

Agent 判断要不要用某个 Skill，靠的是它的描述。所以描述要写：

- 什么场景下用（具体到能匹配你的真实说法）
- 它解决什么问题
- 不适用的情况

只写步骤、不写触发条件的 Skill，大概率不会被用到。

### 复用别人的 Skill

可以，但要先读一遍。别人写的 Skill 隐含了他自己的目录结构、工具和约定，直接拿来往往水土不服。至少把路径、命令、平台相关部分改成本地的。

### 跨工作区复制

Skills 按工作区隔离。把某个项目里打磨好的 Skill 复制到另一个项目时，注意检查它引用的文件路径是否还存在。

### 一个常见误区

以为 Skill 越多 Agent 越强。实际上 Skills 越多，选择成本越高，误触发和该用不用都会增加。**只装当前项目真正需要的**，是提升效果最快的方法。

## 五、MCP 与 CLI

**MCP** 把外部服务变成 Agent 可调用的工具：数据库、项目管理、内部接口、企业系统。

**CLI** 是更轻的一条路：很多服务已经有成熟的命令行工具，Agent 直接调用即可，不需要额外协议层。能用 CLI 解决时，优先用 CLI——它更透明，出问题你能自己复现。

MCP 一样是按项目配置的，理由同上：只给需要它的项目开。

用第三方 MCP 前值得问两个问题：它能读到你哪些数据？它的凭据存在哪？这两点决定风险边界。

## 六、自动任务

### 什么时候值得做成自动任务

判断标准：**这件事会重复发生，而且每次的判断逻辑相同**。

适合：每天汇总某些信息、定时检查项目状态、周期性整理文件、固定格式的日报周报。

不适合：纯提醒（用日程或 Todo 就够）、需要你实时参与判断的事、做完一次就没有下次的事。

### 怎么设计一个好的自动任务

**写清目标，而不是写清步骤。** 目标是稳定的，步骤会随环境变化失效。

**给出判断标准。** "有变化就告诉我"要补充"什么算变化"、"变化多大才值得说"。否则每次运行都会产出一堆噪声。

**让它能自我修正。** 在提示词里允许它根据运行结果调整做法，并说明历史记录在哪。第一次跑出来不好是常态，跑三次之后稳定才是目标。

**控制输出长度。** 长期运行的任务如果每次都输出长文，很快就没人看了。

### 调度

支持单次、固定间隔、每日、每周、每月。间隔型可以限定执行窗口（比如只在工作日上午），也可以设置最大运行次数，避免无限期跑下去。

## 七、子会话与并行探索

### 子会话

子会话是独立的会话，有自己的上下文，但它从属于一个父会话。

适合：

- **深度研究**：父会话保持主线，子会话各自查一块，结论汇回来
- **对抗审查**：一个子会话专门挑毛病，父会话负责修
- **并行处理**：几个互不依赖的子任务同时跑

比传统 SubAgent 的好处是上下文更干净、可以持续迭代、模型可以单独选。

### 探索

探索是从某一轮输出分叉出去，试一条不同的路，结论满意了再带回主会话。

和分叉的区别在于：探索的过程不进主线。你可以在里面问一些边缘问题、试一些可能失败的方向，不会污染主会话的上下文。

用途：方案对比、验证一个不确定的猜想、追一条可能没用的线索。

## 八、远程使用

配好远程连接后（设置 → 远程连接），你可以离开工位用手机下指令，Agent 在你的电脑上执行。

真正有用的不是"远程聊天"，而是**任务不中断**：出门路上想到一件事，发过去，回来时结果已经在了。

注意两点：

- 电脑需要处于唤醒状态，休眠了 Agent 不会执行
- 长时间运行的任务建议配合自动任务或子会话，避免单次会话过长

---

## 九、把工作流沉淀下来

用顺了之后，会自然走向同一个方向：**把重复的判断固化成结构**。

- 反复解释的项目背景 → 写进 `AGENTS.md`
- 反复纠正的做法 → 做成 Skill
- 反复查询的信息 → 做成记忆或索引文件
- 反复执行的流程 → 做成自动任务
- 反复验证的标准 → 写进提示词

每一条都在减少下一次的重复劳动。这也是这个工具真正的用法：不是让模型变聪明，是让它的每一次出手都在已知的约束内。

---

## 结语

上下文质量决定输出质量，这句话在这个工具里是可以操作的：项目层放稳定的、会话层放临时的、记忆里放会改变判断的、Skills 里放容易出错的、自动任务里放会重复的。

边界清楚之后，同一个模型的表现会有明显差别。
